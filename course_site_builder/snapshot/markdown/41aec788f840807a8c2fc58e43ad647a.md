## Abstract
FTC teams can control a motor's speed or position in two ways. They can let the REV hub run its built-in PIDF controller (`setVelocity`, `RUN_TO_POSITION`), or they can write their own PIDF controller inside an OpMode and send motor power every loop. This test measured how quickly each option responds to a new command. Over 20 trials of each of four tests, the OpMode controller started the motor in 9.6–9.9 ms on average, with little variation (standard deviation about 2 ms). The hub controller took 27.9–33.0 ms on average and varied widely from trial to trial (about 8–55 ms). Both controllers receive the same velocity measurement, which was determined to the hub on the hub every 10 ms. The spread in the hub's response times suggests that the hub only updates its motor output every 40–45 ms (roughly 20–25 times per second), while the OpMode controller updated its output at the same rate at the OpMode’s loop time (\~3.35 ms in these tests).
## 1. Background
### 1.1 What a PIDF controller does
A PIDF controller compares where a motor *should* be (the target) with where it *is* (the measurement) and calculates the motor’s power based on the difference. The difference between the two is called the **error**. The controller adds up four terms:
- **P (proportional):** power in proportion to the current error.
- **I (integral):** power based on error that has accumulated over time. This fixes small errors that P alone can't close.
- **D (derivative):** power based on how fast the error is changing. This slows the motor down before it overshoots.
- **F (feedforward):** power based on the target itself, a "best guess" of how much power the target needs before any error appears.
### 1.2 Why update rate matters
A controller only works as well as how often it checks the measurement and changes the power. If it updates 100 times per second, it can correct a problem within about 10 ms. If it updates 20 times per second, a problem can go uncorrected for up to 50 ms. Faster updates generally allow stronger gains and steadier control.
### 1.3 The open question
Neither REV nor FIRST publishes the hub's controller update rate.  Game Manual 0, a community-written FTC guide, states that the hub's built-in PID controller runs at a fixed 20 Hz (once every 50 ms), but gives no source.  This test set out to measure it indirectly.
## 2. Objectives
1. Measure how often the hub updates the velocity reading that both controllers use.
2. Measure the response time of the hub's built-in velocity and position controllers.
3. Measure the response time of equivalent velocity and position controllers written in an OpMode.
4. Use these results to estimate how often the hub's built-in controller updates its output.

The OpMode position controller copies the structure of `RUN_TO_POSITION`: an outer position loop sets a target speed, and an inner velocity loop reaches that speed.
### 4.2 Trial procedure
1. Stop the motor and wait 1.0 s plus a random 0–100 ms.
2. Reset the encoder to 0.
3. Start a timer, then send the command for the current phase.
4. Record position, velocity, power and loop time every loop for 2.0 s.
5. Repeat for the next phase.
The test ran 20 trials of all four phases, about 4 minutes in total. Phases were interleaved (1, 2, 3, 4, 1, 2, 3, 4…) so that slow changes such as battery voltage affected all four phases equally.
The random wait time was used to account for the wait time introduced if the hub acts on a fixed cycle.  A command that arrives at a random moment will sometimes be acted on right away and sometimes have to wait almost a full cycle. Randomizing the start time makes that waiting time show up as spread in the results rather than a consistent error.
To ensure methods were as comparable as possible:
- nothing was sent to telemetry or a dashboard during a phase, and the log was written to a file only after all trials finished. This kept the OpMode loop as fast as possible.
- the timer started *before* each command was sent, so the time to send the command counts against both controllers equally.
- both controllers used the same velocity measurement, `getVelocity()`.
## 5. Data Analysis Methods
### 5.1 Velocity update period
The OpMode sampled the hub's velocity reading every 2–3.4 ms, much faster than the reading changes. Each time the reading changed value, the time since the previous change was recorded as an **update gap**. The gaps were then analyzed two ways:
- **Median of short velocity update gaps:** the median of all gaps under 15 ms.
- **Best-fit period:** candidate velocity update periods from 8.0 to 12.0 ms in 0.1 ms steps were each scored by the average distance from every gap to its nearest multiple of that period. The lowest score is the best fit.
	Multiples of the candidate velocity update period are used because the reading sometimes comes out the same on two updates in a row, which hides an update.
### 5.2 Velocity resolution
The smallest possible change in a measurement is its **resolution**. To find the resolution of the hub's velocity reading, every velocity value logged in all four phases was checked to see whether it was a whole multiple of a common step size, and the size of each change from one reading to the next was recorded.
### 5.3 Response time
**Response time** is the time from sending the command to change the target (`setVolocity` or `setPower` depending on the test phase) until the motor starts moving. For each trial and phase, it was taken as the first sample where the encoder had moved more than 0 ticks from zero (its first tick).
### 5.4 Position versus velocity freshness
Three checks compared how up to date the encoder position and the hub's velocity reading are:
- **Change rate:** while the motor was moving (after the first 0.1 s, with the hub's velocity above 200 ticks/s), the percentage of loops in which each reading changed, and the median time between changes.
- **Steady-speed check:** in Phase 1 between 1.0 and 2.0 s, when the motor runs at a nearly constant 1500 ticks/s, the change in position from one loop to the next was compared with the loop time. If position were only updated on a fixed internal cycle like velocity, many loops would show no change at all.
- **Lag check:** during the first 0.4 s of each Phase 1 trial, the motor's speed was calculated from the change in position over 20 ms (10 ms on either side of each moment). The time this position-based speed reached half the target (750 ticks/s) was compared with the time the hub's velocity reading reached the same value.

## 7. Discussion
### 7.1 Both controllers see the same measurement
All four phases show the same 10 ms velocity update period, including the OpMode phases. This is expected, because the OpMode controller reads the same `getVelocity()` value the hub uses. So the difference between the controllers does *not* come from better measurements. It comes from how quickly each one acts.
The velocity resolution of exactly 20 ticks/s suggests how the hub calculates velocity. If it counts encoder ticks over a fixed time window and divides by the window length, the smallest possible change is one tick per window. A resolution of 20 ticks/s means one tick per 1/20 s, so the window is about **50 ms** (1 tick ÷ 0.05 s = 20 ticks/s). Combined with the 10 ms update period, this suggests the hub recounts the ticks from the last 50 ms every 10 ms. A longer window gives a smoother reading but makes it lag behind sudden speed changes.
### 7.2 Why the custom controller responds faster
At the moment a new target is set, the error is at its largest, so both controllers already "know" they need to push hard. The difference is when they actually apply power.  The **custom controller **sends power on its first loop,  \~3 ms after the command. The motor then takes about another \~6–7 ms to turn far enough for the encoder's first tick. These add to a consistent total of \~10 ± 2 ms.  The **built-in controller **waits for its next output update, which can come anywhere from 0–43 ms later , averaging about 28–33 ms.
### 7.3 Estimating the hub's output update rate
The built-in controller's shortest response times (8.3–11.9 ms) are close to the custom controller's steady value. That is what happens when a command arrives just before the hub's next update. The longest hub times are about 40 ms later, when a command arrives just after an update.
If values are spread evenly across a range of width $`W`$, their standard deviation is:
$$
\sigma = \frac{W}{\sqrt{12}}
$$
Solving for $`W`$ with the hub's standard deviation of about 12.5 ms gives $`W \approx 12.5 \times 3.46 \approx 43`$ ms. This matches the observed ranges of 40–43 ms (11.9–54.8 ms for velocity, 8.3–47.9 ms for position). Together these suggest that the **hub updates its motor output about every 40–45 ms (about 22–25 Hz)**, even though its velocity reading updates every 10 ms. This is close to the 20 Hz figure reported in Game Manual 0.
### 7.4 When the custom controller advantage holds
The OpMode controller's advantage depends on a fast OpMode loop time.  The custom controller waits about half a loop on average before acting, and the built-in controller waits about half its cycle. They break even when the OpMode’s loop time is about as slow as the built-in controller’s cycle, roughly 40 ms (see 7.4 below).  
The custom controller’s advantage does not scale linearly.  At loop loop times just below 10 ms will get a new velocity reading every loop and yield response times of \~10 ms.  However, if loop time rises just above 10 ms the controller will miss miss velocity reading updates and have response times \~20 ms.
The built-in controller may perform better when OpMode loop times vary significantly from loop to loop.  A loop that is usually fast but sometimes exceeds 40 ms (for example, because of vision processing or I2C sensor reads) can perform worse than the built-in controllers 10–43 ms cycle.
### 7.5 Position is fresher than velocity
The position reading changed on every loop at steady speed, and the size of each change grew with the loop time (about 1.5 ticks per millisecond, matching the motor's speed). This implies the hub reports the encoder count as it is at the moment of each bulk read. The velocity reading, by contrast, changed on only about 1 loop in 10, because it is only recalculated every 10 ms.
The hub's velocity reading also **lags** the motor's actual speed, as measured by consecutive position measurmentes, by about 33 ms. This fits the 50 ms averaging window from section 7.1. An average over the last 50 ms describes the speed about 25 ms ago. Waiting for the next 10 ms update adds about 5 ms on average, and reading the value adds a few more for a total of \~33 ms.
A custom **position** controller sees a position error within one loop (2–3 ms here).  OpModes with loop times under 10 ms can react far sooner than anything that the `RUN_TO_POSITION` command which depends on the hub’s velocity measurement with period of 10 ms.
Further, custom **velocity** controllers that use `getVelocity()` reacts to speed changes about 33 ms late, which is similar to the hub's own output delay.  A custom controller can calculate velocity itself from the change in position since the last loop (\~3 ms).  This would lead to faster responses but would be significantly noiser and would require smoothing in practice.
## 8. Sources of Error and Limitations
- The hub's 40–43 ms output cycle is **inferred** from the spread of response times, not measured directly. REV has not confirmed it.
- Only one Control Hub, one motor, one firmware version and one set of gains were tested, with no load on the motor.
- Timing resolution is limited by the loop time (2–3.4 ms), so each event may be seen up to one loop late.
- The custom controller's gains were not matched in behavior to the hub's, so only timing is compared, not control quality.
- The motor's own startup time (about 6–7 ms here) is included in every response time. It would be different for other motors or under load.
## 9. Major conclusions
1. The hub updates its velocity reading every **10 ms**, calculated from encoder ticks averaged over a 50 ms window. Both the built-in and custom controllers use this same reading.
2. The custom PIDF controller responded to new commands in **9.6–9.9 ms** on average, with little variation (standard deviation about 2 ms).
3. The hub's built-in controller responded in **27.9–33.0 ms** on average, with wide variation (standard deviation about 12.5 ms, range about 8–55 ms).
4. The pattern of the hub's response times suggests it updates its motor output about every **40–45 ms**, which supports Game Manual 0's 20 Hz figure.
5. An OpMode PIDF controller responds about 3 times faster, as long as the OpMode loop stays fast and steady.
6. Encoder position is up to date on every bulk read (it changed on 100% of loops at steady speed), while the hub's velocity reading lags the motor's actual speed by about **33 ms**. Custom controllers that act on position, or on velocity calculated from position, can react much sooner than ones that use `getVelocity()`.
## 10. Recommendations
- **Use an OpMode PIDF** for mechanisms where response time matters, such as arms, slides and flywheels that must recover quickly after a shot. Keep the loop at or under about 10 ms with bulk reads, and avoid slow I2C reads and heavy processing in the same loop.
- **Use the hub's built-in controller** for simple jobs where a delay of up to \~55 ms doesn't matter. It costs the OpMode no time, and slow OpMode code doesn't affect its timing.
- **For position control**, a custom controller has an extra advantage: encoder position is fresh on every bulk read, while the hub's velocity reading lags actual speed by about 33 ms (sections 6.6 and 7.6).
- **To get past the 10 ms velocity limit**, teams may calculate velocity in the OpMode from the change in encoder position, with some filtering to reduce noise.

/*
 * PIDF Response Test (multi-trial, log-file writer)
 * --------------------------------------------------
 * One motor named "TEST" on the Control Hub, free to spin.
 *
 * Each trial runs four phases in order:
 *   1  HUB velocity step     RUN_USING_ENCODER + setVelocity(VEL_TARGET)
 *   2  CUSTOM velocity step  same PIDF gains, computed here, setPower()
 *   3  HUB position step     RUN_TO_POSITION, capped at POS_MAX_VEL
 *   4  CUSTOM position step  position P -> velocity PIDF, computed here
 *
 * Phases are interleaved (1,2,3,4,1,2,3,4...) so slow drift such as
 * battery voltage affects all four phases equally.
 *
 * Between phases the motor rests for REST_MS plus a random 0-REST_JITTER_MS.
 * The jitter makes each command land at a random point in the hub's internal
 * cycle. If the hub only updates its output every X ms, the response time across
 * trials will spread evenly over a range about X ms wide.
 *
 * The custom controller reads the gains from the hub at start, so it uses the
 * same numbers as the built-in one. Unit assumptions (REV doesn't publish them):
 *   power = (P*e + I*integral + D*de/dt + F*target) / 32767, with e in ticks/s
 *   integral and derivative use seconds
 *   position loop: velocity target = posP * (position error in ticks)
 *
 * Nothing goes to telemetry or a dashboard while a phase runs. Samples go into
 * memory, and the CSV is written once at the end (also if you press STOP early).
 *
 * Log file: /sdcard/FIRST/logs/pidf_test_<date>_<time>.csv
 * Columns:  trial, phase, t_s, loop_ms, target, pos_ticks, vel_tps, power
 *   t_s   = seconds since the command for that phase was sent
 *   power = commanded power (custom phases only; blank for hub phases)
 */
@TeleOp(name = "PIDF Response Test", group = "Test")
public class PIDFResponseTest extends LinearOpMode {

    // ---------- Test setup ----------
    static final int     TRIALS         = 20;     // trials of each phase
    static final boolean REVERSE_MOTOR  = false;  // flip if positive power gives negative ticks
    static final double  VEL_TARGET     = 1500;   // ticks/s
    static final int     POS_TARGET     = 1000;   // ticks
    static final double  POS_MAX_VEL    = 2000;   // ticks/s cap for both position tests
    static final double  TEST_TIME_S    = 2.0;    // recording time per phase
    static final long    REST_MS        = 1000;   // pause between phases
    static final long    REST_JITTER_MS = 100;    // extra random pause, 0..this

    // ---------- Recording buffers ----------
    // ~800 samples per phase x 4 phases x 20 trials = ~64,000 rows
    static final int MAX_SAMPLES = 150000;
    final short[]  trialBuf  = new short[MAX_SAMPLES];
    final byte[]   phaseBuf  = new byte[MAX_SAMPLES];
    final double[] tBuf      = new double[MAX_SAMPLES];
    final double[] loopBuf   = new double[MAX_SAMPLES];
    final double[] targetBuf = new double[MAX_SAMPLES];
    final int[]    posBuf    = new int[MAX_SAMPLES];
    final double[] velBuf    = new double[MAX_SAMPLES];
    final double[] powerBuf  = new double[MAX_SAMPLES];
    int n = 0;

    DcMotorEx motor;
    List<LynxModule> hubs;
    PIDFCoefficients velGains, posGains;
    final Random random = new Random();
    int trial = 0;

    @Override
    public void runOpMode() {
        motor = hardwareMap.get(DcMotorEx.class, "TEST");
        motor.setDirection(REVERSE_MOTOR ? DcMotor.Direction.REVERSE
                                         : DcMotor.Direction.FORWARD);
        motor.setZeroPowerBehavior(DcMotor.ZeroPowerBehavior.BRAKE);

        hubs = hardwareMap.getAll(LynxModule.class);
        for (LynxModule hub : hubs) hub.setBulkCachingMode(LynxModule.BulkCachingMode.MANUAL);

        velGains = motor.getPIDFCoefficients(DcMotor.RunMode.RUN_USING_ENCODER);
        posGains = motor.getPIDFCoefficients(DcMotor.RunMode.RUN_TO_POSITION);

        double minutes = TRIALS * 4 * (TEST_TIME_S + (REST_MS + REST_JITTER_MS / 2.0) / 1000.0) / 60.0;
        telemetry.addData("Velocity gains", "P%.2f I%.2f D%.2f F%.2f",
                velGains.p, velGains.i, velGains.d, velGains.f);
        telemetry.addData("Position P", "%.2f", posGains.p);
        telemetry.addData("Trials", "%d  (about %.1f min)", TRIALS, minutes);
        telemetry.addLine("Motor must spin freely. Press START.");
        telemetry.update();

        waitForStart();

        for (trial = 1; trial <= TRIALS && opModeIsActive(); trial++) {
            status("HUB velocity", 1);
            if (opModeIsActive()) runHub(1, false);
            status("CUSTOM velocity", 2);
            if (opModeIsActive()) runCustom(2, false);
            status("HUB position", 3);
            if (opModeIsActive()) runHub(3, true);
            status("CUSTOM position", 4);
            if (opModeIsActive()) runCustom(4, true);
        }

        motor.setPower(0);
        telemetry.addData("Status", "Writing log...");
        telemetry.update();
        String result = writeLog();

        while (opModeIsActive()) {
            telemetry.addData("Status", "Done");
            telemetry.addData("Samples", n);
            telemetry.addData("Log", result);
            telemetry.update();
            sleep(500);
        }
    }

    // ===================== Built-in hub controller =====================
    void runHub(int phase, boolean positionMode) {
        rest();
        if (positionMode) {
            motor.setTargetPosition(POS_TARGET);
            motor.setMode(DcMotor.RunMode.RUN_TO_POSITION);
        } else {
            motor.setMode(DcMotor.RunMode.RUN_USING_ENCODER);
        }
        double target = positionMode ? POS_TARGET : VEL_TARGET;

        long t0 = System.nanoTime();               // clock starts before the command is sent
        long last = t0;
        motor.setVelocity(positionMode ? POS_MAX_VEL : VEL_TARGET);

        while (opModeIsActive() && n < MAX_SAMPLES) {
            long now = System.nanoTime();
            double t = (now - t0) * 1e-9;
            if (t > TEST_TIME_S) break;
            double loopMs = (now - last) * 1e-6;
            last = now;

            clearCache();
            record(phase, t, loopMs, target, motor.getCurrentPosition(), motor.getVelocity(), Double.NaN);
        }
        motor.setVelocity(0);
        motor.setPower(0);
    }

    // ===================== Custom OpMode controller =====================
    void runCustom(int phase, boolean positionMode) {
        rest();
        motor.setMode(DcMotor.RunMode.RUN_WITHOUT_ENCODER);
        double target = positionMode ? POS_TARGET : VEL_TARGET;

        double kP = velGains.p, kI = velGains.i, kD = velGains.d, kF = velGains.f;
        double posP = posGains.p;
        double integral = 0, lastErr = 0;
        double iLimit = (kI > 0) ? 32767.0 / kI : 0;   // keep I term within full scale

        long t0 = System.nanoTime();
        long last = t0;
        boolean first = true;

        while (opModeIsActive() && n < MAX_SAMPLES) {
            long now = System.nanoTime();
            double t = (now - t0) * 1e-9;
            if (t > TEST_TIME_S) break;
            double dt = (now - last) * 1e-9;
            last = now;

            // read: one bulk read gives position and velocity
            clearCache();
            int pos = motor.getCurrentPosition();
            double vel = motor.getVelocity();

            // outer position loop (same cascade as RUN_TO_POSITION)
            double velTarget = positionMode
                    ? Range.clip(posP * (POS_TARGET - pos), -POS_MAX_VEL, POS_MAX_VEL)
                    : VEL_TARGET;

            // inner velocity PIDF, output on the hub's +/-32767 scale
            double err = velTarget - vel;
            double deriv = 0;
            if (!first) {
                integral = Range.clip(integral + err * dt, -iLimit, iLimit);
                if (dt > 0) deriv = (err - lastErr) / dt;
            }
            lastErr = err;
            first = false;

            double power = Range.clip(
                    (kP * err + kI * integral + kD * deriv + kF * velTarget) / 32767.0, -1, 1);

            // write
            motor.setPower(power);

            record(phase, t, dt * 1000, target, pos, vel, power);
        }
        motor.setPower(0);
    }

    // ===================== Helpers =====================

    /** Stop, let the motor come to rest (plus random jitter), reset the encoder. */
    void rest() {
        motor.setMode(DcMotor.RunMode.RUN_WITHOUT_ENCODER);
        motor.setPower(0);
        long jitter = REST_JITTER_MS > 0 ? (long) (random.nextDouble() * REST_JITTER_MS) : 0;
        sleep(REST_MS + jitter);
        motor.setMode(DcMotor.RunMode.STOP_AND_RESET_ENCODER);
    }

    void clearCache() {
        for (LynxModule hub : hubs) hub.clearBulkCache();
    }

    void record(int phase, double t, double loopMs, double target, int pos, double vel, double power) {
        trialBuf[n] = (short) trial;
        phaseBuf[n] = (byte) phase;
        tBuf[n] = t;
        loopBuf[n] = loopMs;
        targetBuf[n] = target;
        posBuf[n] = pos;
        velBuf[n] = vel;
        powerBuf[n] = power;
        n++;
    }

    void status(String name, int phase) {
        telemetry.addData("Trial", "%d of %d", trial, TRIALS);
        telemetry.addData("Phase", "%d: %s", phase, name);
        telemetry.addData("Samples", "%d / %d", n, MAX_SAMPLES);
        telemetry.update();
    }

    /** Round to a fixed number of decimal places without String.format (much faster for big logs). */
    static double round(double x, double scale) {
        return Math.round(x * scale) / scale;
    }

    String writeLog() {
        File dir = new File(AppUtil.FIRST_FOLDER, "logs");
        if (!dir.exists()) dir.mkdirs();
        String stamp = new SimpleDateFormat("yyyyMMdd_HHmmss", Locale.US).format(new Date());
        File file = new File(dir, "pidf_test_" + stamp + ".csv");

        try (FileWriter w = new FileWriter(file)) {
            w.write(String.format(Locale.US,
                    "# vel gains P=%.3f I=%.3f D=%.3f F=%.3f, pos P=%.3f, VEL_TARGET=%.0f, POS_TARGET=%d, POS_MAX_VEL=%.0f, TRIALS=%d\n",
                    velGains.p, velGains.i, velGains.d, velGains.f, posGains.p,
                    VEL_TARGET, POS_TARGET, POS_MAX_VEL, TRIALS));
            w.write("trial,phase,t_s,loop_ms,target,pos_ticks,vel_tps,power\n");

            StringBuilder sb = new StringBuilder(1 << 20);
            for (int i = 0; i < n; i++) {
                sb.append(trialBuf[i]).append(',')
                  .append(phaseBuf[i]).append(',')
                  .append(round(tBuf[i], 1e5)).append(',')
                  .append(round(loopBuf[i], 1e3)).append(',')
                  .append(targetBuf[i]).append(',')
                  .append(posBuf[i]).append(',')
                  .append(velBuf[i]).append(',');
                if (!Double.isNaN(powerBuf[i])) sb.append(round(powerBuf[i], 1e4));
                sb.append('\n');
                if (sb.length() > (1 << 19)) {      // flush in chunks
                    w.write(sb.toString());
                    sb.setLength(0);
                }
            }
            w.write(sb.toString());
            return file.getAbsolutePath();
        } catch (IOException e) {
            return "WRITE FAILED: " + e.getMessage();
        }
    }
}
