## Introduction
A robot can be programmed to move without any reference to control theory. Switching a motor on, waiting for a fixed interval, and switching it off will produce motion, and many first attempts at autonomous robot programs take exactly this form. Such programs rarely produce the same result twice, however. A routine that performs reliably in testing may fall well short of its target under slightly different conditions. The cause is seldom an error in the code. Rather, the code issues commands based on assumptions about how the machine will respond to real world conditions, but the real world rarely cooperates.
The task of nearly every robotic mechanism can be reduced to reaching a target state and maintaining it: a drivetrain that stops at a specified position, a lift that holds a height while a gripper releases its load, a flywheel that maintains a constant speed so that each projectile leaves with the same velocity. A <span color="red">**`controller`**</span> is the component of a system, usually implemented in software, that determines the commands sent to an actuator so that the mechanism reaches its target quickly, and remains there even in the presence of external forces.
Controllers are ubiquitous in engineered systems. A household thermostat measures room temperature and cycles the furnace to hold that temperature steady. An automobile's cruise control measures vehicle speed and adjusts the throttle as the road grade changes. A quadcopter cannot remain airborne at all without a controller adjusting the speed of each rotor hundreds of times per second to keep the vehicle level. The branch of engineering concerned with the analysis and design of such controllers is called <span color="red">**`control theory`**</span>. Some systems are straightforward to control, others are difficult, and some cannot be controlled at all. The ability to distinguish among these cases is fundamental to nearly every engineering discipline that produces machines.
<callout color="gray_bg">
	When a SpaceX Falcon 9 booster returns from space and lands upright on a drone ship, no pilot steers it. Its guidance software measures the booster's position, velocity, and orientation many times per second and continuously adjusts its engine and steering fins to correct for wind and other errors during descent. Although far more sophisticated, the system applies the same principle used to hold a robotic arm at a fixed angle: measure the current state, compare it to the target, apply a correction, and repeat.
</callout>

This reading covers four big ideas in control theory:
1. **Open Loop Control**: commanding an actuator without measuring the result
2. **Closed Loop Control**: measuring the result and correcting for error
3. **PID Control**: a controller that uses three separate calculations to control how quickly and how stably an actuator approaches its target 
4. **Feedforward Control**: using physics to predict the output an actuator requires before error accumulates

## Open Loop Control
The simplest control strategy is to determine in advance what a machine should do and then execute that plan. An <span color="red">**`open loop controller`**</span> issues commands without measuring their result. A toaster is an open loop controller: it heats bread for a fixed duration regardless of whether the bread began frozen or already toasted. A timed lawn sprinkler is another example: it runs for 20 minutes each morning, even during a rainstorm.
The most basic method of moving a robot follows the same pattern: switch the drive motors on, wait, and switch them off. 
The block diagram below shows the logic behind open loop control.
![](media/77364aaacc5c308c.png)
The following pseudocode example is written for an FTC robot.
```java
// An open loop controller
loop() {
    if (time.seconds() < 0.5) {
        power = 1;
    } else {
        power = 0;
    }
    motor.setPower(power);
}
```
Note what this code actually specifies. It does not command the robot to travel 1 meter; it commands full power for half a second. The distance traveled is simply whatever results from that power applied over that time. The code therefore depends on an assumption about how the system responds to a given command. In this case, the model is that full power for 0.5 seconds moves the robot a set distance.
### Disturbances
Any influence that alters a system's response to a command, but is not part of the command itself, is a <span color="red">**`disturbance`**</span>. Because an open loop controller cannot detect disturbances, each one appears directly as error in the result. Mobile robots are subject to many disturbances:
- **Battery voltage.** Most motor controllers interpret a power command as a fraction of the available supply voltage, not as a speed. A full-power command (`setPower(1)` in FTC) applies 100% of whatever voltage the battery supplies at that moment. A nominal 12 V robot battery may exceed 13.5 V when fully charged and fall toward 12 V with use. Because a DC motor's speed is approximately proportional to its applied voltage, the same command produces slower motion as the battery discharges.
- **Mass.** A heavier robot accelerates and decelerates more slowly. Adding a mechanism or carrying a payload changes the distance produced by the same power applied for the same duration.
- **Friction and traction.** Worn wheels and bearings, dust, or a change in floor surface alter the fraction of the motor's effort that is converted into motion.
- **Starting position.** If the robot begins slightly misaligned, an open loop routine follows the misaligned path faithfully and never corrects it.
- **Contact.** A collision with an obstacle or another robot can push the system off course, and an open loop controller has no means of detecting that it occurred.
These errors also accumulate. In a multi-step autonomous sequence, each motion begins wherever the previous one ended, so a small error in the first motion grows larger with each subsequent step.
<callout color="gray_bg">
	**Competition Robotics Example**
	During practice, an FTC team tunes a timed autonomous routine using a freshly charged battery that measures 13.8 V. The robot drives forward 150 cm and parks accurately on every run.
	At competition, after several matches, the battery measures 12.6 V. Because motor speed is approximately proportional to voltage, the robot now moves at about 12.6 ÷ 13.8 ≈ 91% of its practice speed. In the same interval it travels about 137 cm, stopping 13 cm short of the parking zone.
	*The code did not change; the disturbance did. The team's model ("this power for this duration moves the robot 150 cm") was valid only at a single battery voltage.*
</callout>
### When Open Loop Control Is Sufficient
Open loop control is not inherently inadequate. It performs well when the precise result is unimportant, or when something outside the controller is already monitoring the result.
- **The precise result is unimportant.** An intake roller that runs at full power whenever the operator holds a trigger does not need to reach a precise speed; it only needs to draw objects in.
- **A human operator is observing.** When a robot is driven manually (during the driver-controlled period of an FTC match, for example), the drive code is open loop: joystick position in, motor power out. The operator, however, watches the robot and adjusts the joysticks continuously. The operator's eyes act as the sensor and the operator's brain acts as the controller. This arrangement is called a <span color="red">**`human in the loop`**</span>, and it explains why open loop drive code performs acceptably under manual control but poorly in autonomous operation, where no one is present to correct it.
A useful question to ask of any mechanism is: *Would a 10% error in the result matter?* If it would, the controller must measure the result rather than assume it.
<callout color="gray_bg">
	<details>
	<summary>🔵 <span color="blue">**Advanced Open Loop: Correcting for a Known Disturbance**</span></summary>
		When a disturbance is known in advance and can be measured, an open loop controller can be improved by incorporating that disturbance into its model. Battery voltage is a common example. Many robot control systems can measure supply voltage (in FTC, the REV Control Hub reports it), so the program can scale motor power to compensate for a partially discharged battery.
		```java
// Read the battery voltage from the Control Hub
VoltageSensor battery = hardwareMap.voltageSensor.iterator().next();

// The battery voltage when the routine was tuned
double NOMINAL_VOLTAGE = 13.0;

// Scale the power up as the battery drains
double power = 0.8 * (NOMINAL_VOLTAGE / battery.getVoltage());
power = Math.min(power, 1.0);   // motor power can't go above 1
		```
		Two features of this code deserve attention:
		- **It requires headroom.** The routine is tuned at 0.8 power rather than full power, which leaves room to increase the command when the battery is low. A routine tuned at full power cannot be compensated, because no command above 1 is available.
		- **It corrects only the disturbance that was modeled.** Voltage compensation does nothing to address added mass, reduced traction, a misaligned start, or a collision. To correct for disturbances that were *not* predicted, the controller must measure the result, which is the subject of the next section.
		Using a model to predict and cancel a disturbance before it produces error is a simple form of <span color="red">**`feedforward`**</span>, which is treated in more detail at the end of this reading.
	</details>
</callout>

## Closed Loop Control
The limitations of open loop control share a common cause: the controller never learns what actually happened. The remedy is to give the controller the role that a human operator plays during manual driving. A sensor observes the mechanism, and the controller compares that observation to the goal before deciding on its next command. This approach does not require a perfect model of the system or an inventory of every disturbance it might encounter. The controller needs to know only how far the mechanism is from its target and in which direction. Whatever caused the deviation, whether a weak battery, an added payload, or a collision, appears in the measurement and can therefore be corrected.
A <span color="red">**`closed loop controller`**</span> measures the actual state of the mechanism, compares it to the desired state, and adjusts its output to reduce the difference. Closed loop control relies on <span color="red">**`feedback`**</span>: each measurement informs the next command. Every closed loop controller has four elements:
- The <span color="red">**`target`**</span> (or **`setpoint`**): the desired state of the mechanism. Ex. an arm at 85 degrees.
- The <span color="red">**`measurement`**</span>: the current state of the mechanism, as reported by a sensor. Ex. the arm motor's angle sensor reads 10 degrees.
- The <span color="red">**`error`**</span>: the target minus the measurement. Ex. 85 - 10 = 75 degrees.
- The <span color="red">**`output`**</span>: the command the controller sends to the actuator to reduce the error.
The controller executes this cycle repeatedly within the program's main loop: measure →  compute the error → compute the output → send it to the actuator, and repeat. Because it measures the result on every cycle, a closed loop controller can correct for a low battery, a heavier mechanism, or an external force, none of which an open loop controller can detect.

## The Bang-Bang Controller
The simplest form of closed loop control is simply to run a motor at a set power toward the target.  When the measurement is less than the target, run the motor forward.  And when the measurement is greater than the target, run the motor in reverse.  This results in a mechanisms constantly oscillating around the target, but rarely settling.
The diagram and pseudocode below show how a bang-bang controller works.
 
![](media/3cf06905cffc1a0f.png)
```java
// A bang-bang controller
loop() {
    if (measurement < target) {
        power = 1;
    } else {
        power = -1;
    }
    motor.setPower(power);
}
```
Although the bang-bang controller measures the result, it makes only limited use of that measurement. The controller asks a single question, whether the mechanism is below or above the target, and responds with one of only two outputs. It applies the same full power whether the arm is 75 degrees from the target or 0.5 degrees from it. As a result, in practice, the mechanism approaches the target at full speed, and its momentum carries it past. The controller then reverses at full power, the mechanism overshoots in the opposite direction, and the cycle repeats indefinitely. Because no output in this code corresponds to holding still, the mechanism never settles, even when it is exactly on target.
This constant reversal has practical costs as well. Each change in direction subjects gears, shafts, and couplings to shock loads, draws large currents from the battery, and heats the motor. The oscillation also limits precision: at any given moment, the mechanism's position is wherever the most recent swing happened to carry it.
Bang-bang control remains appropriate for systems that respond slowly or whose actuators can only be switched fully on or off. A household furnace is one example: it cannot run at partial output, and room temperature changes so gradually that brief overshoot is harmless. Such systems typically define a small band around the target, called a deadband, within which the controller takes no action, which prevents rapid switching. For a mechanism with significant mass and a motor capable of variable output, however, an effective controller should scale its response to the size of the error, applying a strong correction when the mechanism is far from the target and a gentle one as it draws near.

## PID Control
The most widely used closed loop controller, both in robotics and across industry, is the <span color="red">**`PID controller`**</span><span color="red">**  **</span>which stands for proportional-integral-derivative controller.  Although you may recognize the terms *integral* and *derivative* from calculus, no calculus is required to understand the principles behind this controller.  To build an understanding of how a PID controller works, we will look at one term of the controller at a time.
### P: Proportional Controller
The <span color="red">**`proportional term`**</span> of the PID produces an output proportional to the current error: a large error yields a strong correction, and a small error yields a weak one. This creates a high output power when the error is large moving the mechanism toward the target quickly.  As the error decreases, the output gets smaller and a the mechanism slows down.  The proportional term of a PID controller does most of the work to bring the mechanism close to the target.  In many applications, where a high degree of accuracy is not required, a proportional controller is sufficient and the integral and derivative terms are not used.
The block diagram and pseudocode below show how the proportional controller adjusts its output in response to the size of the error.  
![](media/7a44b5afe46af07e.png)
```java
// A Proportional controller
loop() {
    error = target - measurement;
	  P = error * Kp; // Kp is a constant 
	  power = P;
    motor.setPower(power);
}
```
In the diagram and code $`K_P`$ is called the `proportional gain`  which is a constant that determines how strongly the motor power responds to the error.  A controller with a large $`K_P`$ will move toward the target faster than a controller with a small $`K_P`$.
Used alone, proportional control exhibits two characteristic problems. 
	- If $`K_p`$ is too large, it acts like a bang-bang controller: the mechanism gains excessive speed, passes the target, and swings back and forth across it (<span color="red">**`overshoot`**</span> and <span color="red">**`oscillation`**</span>). 
	- If a persistent force such as gravity or friction opposes the motion, the mechanism stops short of the target, because near the target the error, and therefore the motor power becomes to small to overcome that force. The remaining gap is called <span color="red">**`steady-state error`**</span>.
### PI: Proportional-Integral Controller
Adding the <span color="red">**`integral term`**</span> to a controller uses the accumulated error over time to overcome any error that the proportional term can’t handle. As long as the mechanism remains short of its target, the accumulated error continues to grow, and the integral term applies an increasingly strong correction until the error is eliminated. The integral term is therefore the means by which steady-state error is removed.
The graph below shows how the accumulated error is calculated.  During each control loop, the error is multiplied by the elapsed time since the last calculation (∆t).  The product $`error \times \Delta t`$ gives the area of each rectangle.  Those areas are added to produce the accumulated error.  (This is the `integralSum` in the pseudocode below).  If an error, even a small one, persists for a long time, the accumulated error continues to grow, eventually becoming large enough to add significantly to the output and nudge the mechanism to overcome the last bit of error.
![](media/b3c8de69dff926df.png)
<empty-block/>
The diagram and pseudocode below show the logic behind the integral term of a PI controller.
![](media/7195ac917a5e64c4.png)
```java
// A Proportional-Integral controller
integralSum = 0;
loop() {
    error = target - measurement;
    integralSum = errorSum + (error * timer.seconds());
    
	  P = error * Kp; // Kp is a constant 
	  I = integralSum * Ki; // Ki is a constant 
	  
	  power = P + I;
    motor.setPower(power);
    
    timer.reset();
}
```
### PID: Proportional-Integral-Derivative Controller
<span discussion-urls="discussion://3f7ec788-f840-81d0-a468-e7be52d79e62/bb6cc2b2-0ebf-4d66-9d1c-a3739a7e269e/401ec788-f840-80d9-b1b5-001c55f7b049">The </span><span color="red" discussion-urls="discussion://3f7ec788-f840-81d0-a468-e7be52d79e62/bb6cc2b2-0ebf-4d66-9d1c-a3739a7e269e/401ec788-f840-80d9-b1b5-001c55f7b049">**`derivative term`**</span><span discussion-urls="discussion://3f7ec788-f840-81d0-a468-e7be52d79e62/bb6cc2b2-0ebf-4d66-9d1c-a3739a7e269e/401ec788-f840-80d9-b1b5-001c55f7b049"> calculates the rate at which the error is changing. As the mechanism approaches its target rapidly, the error decreases quickly, this makes the derivative term large and negative, so the derivative term </span>***<span discussion-urls="discussion://3f7ec788-f840-81d0-a468-e7be52d79e62/bb6cc2b2-0ebf-4d66-9d1c-a3739a7e269e/401ec788-f840-80d9-b1b5-001c55f7b049">subtracts</span>***<span discussion-urls="discussion://3f7ec788-f840-81d0-a468-e7be52d79e62/bb6cc2b2-0ebf-4d66-9d1c-a3739a7e269e/401ec788-f840-80d9-b1b5-001c55f7b049"> from the proportional and integral terms to slow the mechanism’s approach toward the target.  In this way the derivative term </span><span color="red" discussion-urls="discussion://3f7ec788-f840-81d0-a468-e7be52d79e62/bb6cc2b2-0ebf-4d66-9d1c-a3739a7e269e/401ec788-f840-80d9-b1b5-001c55f7b049">**`damps`**</span><span discussion-urls="discussion://3f7ec788-f840-81d0-a468-e7be52d79e62/bb6cc2b2-0ebf-4d66-9d1c-a3739a7e269e/401ec788-f840-80d9-b1b5-001c55f7b049"> the motion, reducing overshoot and oscillation.</span>
The block diagram and pseudocode below shows how the derivative term is implemented.
![](media/890bef5cdcc4f822.png)
```java
// A Proportional-Integral-Derivative controller
integralSum = 0;
lastError = 0;
loop() {
    error = target - measurement;
    integralSum = errorSum + (error * timer.seconds()); 
	  derivative = (error - lastError) / timer.seconds();
	  
	  P = error * Kp; // Kp is a constant 
	  I = integralSum * Ki; // Ki is a constant 
	  D = derivative * Kd; // Kd is a constant
	  
	  power = P + I + D;
    motor.setPower(power);
    
    lastError = error;
    timer.reset();
}
```
<callout color="gray_bg">
	<details>
	<summary>🔵 <span color="blue">**Advanced PID: Real-World Problems**</span></summary>
		The pseudocode above is functional, but physical mechanisms expose three common problems that a robust implementation must address.
		- <span color="red">**`Integral windup`**</span>: if the mechanism is prevented from moving (blocked by an obstruction, or deliberately held in place), `integralSum` continues to grow. When the mechanism is released, the accumulated integral term drives it well past the target. Common remedies include limiting `integralSum` to a maximum magnitude and resetting it to zero whenever the target changes.
		- <span color="red">**`Derivative kick`**</span>: on the first pass, `lastError` is 0, so the apparent change in error is very large and the derivative term produces a sharp spike in output. The same effect occurs whenever the target changes abruptly. Common remedies include initializing `lastError` to the current error before the loop begins, or computing the derivative from the change in *measurement* rather than the change in error.
		- <span color="red">**`Sensor noise`**</span>: differentiation amplifies small, rapid fluctuations, so a noisy sensor (a distance sensor, for example) produces an erratic derivative term. A low-pass filter, such as a running average of the derivative over several passes, attenuates this noise.
	</details>
</callout>

## Feedforward Control
Feedback can respond only *after* error appears. For many mechanisms, however, we can predict the required output  before any motion occurs. A linear slide requires some power simply to support its own weight against gravity. A drivetrain requires some power to overcome static friction before its wheels begin to turn. <span color="red">**`Feedforward control`**</span> uses knowledge of the mechanism to predict this output and adds it directly to the command, so that the feedback terms need only correct the error in the prediction.
The simplest feedforward term is a constant, $`K_f`$, added to the PID output. This term is the "F" in a <span color="red">**`PIDF controller`**</span>.  This is shown in the block diagram and pseudocode below.
![](media/9f9d32507e79964d.png)
```java
// A Proportional-Integral-Derivative-Feedforward controller
integralSum = 0;
lastError = 0;
loop() {
    error = target - measurement;
    integralSum = errorSum + (error * timer.seconds()); 
	  derivative = (error - lastError) / timer.seconds();
	  
	  P = error * Kp; // Kp is a constant 
	  I = integralSum * Ki; // Ki is a constant 
	  D = derivative * Kd; // Kd is a constant
	  F = Kf; // Kf is a constant
	  
	  power = P + I + D + F;
    motor.setPower(power);
    
    lastError = error;
    timer.reset();
}
```
<empty-block/>
<callout color="gray_bg">
	<details>
	<summary>🔵 <span color="blue">**Advanced Feedforward: Matching the Model to the Mechanism**</span></summary>
		A constant $`K_f`$ is an appropriate model for a linear slide, because gravity exerts the same force on it at every height. Other mechanisms require different models:
		- **Arm:** the gravitational torque on a rotating arm depends on its angle. It is greatest when the arm is horizontal and zero when the arm is vertical. A common arm feedforward model is $`K_{grav} \cdot \cos(\theta)`$, where $`\theta`$ is the arm's angle measured from horizontal.
		- **Velocity control (flywheels, drivetrains):** the required power increases with the target speed. A common model is $`K_s + K_v \cdot v_{target}`$, where $`K_s`$ is the power required to overcome static friction and $`K_v`$ is the additional power required per unit of speed.
		Selecting a feedforward model is an engineering decision. It requires an understanding of the mechanism's physics, not merely adjusting numbers until the behavior appears acceptable.
	</details>
</callout>
