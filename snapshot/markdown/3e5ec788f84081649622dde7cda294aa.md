Can you write working robot code without ever thinking about architecture first? Sure. Plenty of rookie teams start typing `motor.setPower()` the moment they get a controller in hand, and the robot moves. But the moment more than one person touches the code, or the robot grows past two or three mechanisms, undesigned code starts to show its limitations: one giant OpMode file with five hundred lines of if-statements, a teammate's fix to the intake silently breaking the lift, nobody quite sure which variable actually controls what anymore. Professional software engineers hit this same wall on every project bigger than a weekend script. The answer they've converged on is ***system architecture***: deciding how the system will be organized before you fill in the details, the same way you wouldn't start framing a house before carefully designing where the walls, doors, and windows go.
<callout color="gray_bg">
	Real spacecraft software runs into the exact same problem at a much higher stakes. NASA's [core Flight System (cFS)](https://www.coreflightsystem.net/) flies on dozens of different missions by organizing flight software into independent "apps," each one owns exactly one job (attitude control, telemetry, command handling) and they talk to each other over a shared message bus instead of reaching into each other's internals. That's the same idea a four-subsystem FTC robot uses at a much smaller scale: Drivetrain, Intake, Lift, and Outtake shouldn't reach into each other's fields. Each one owns one job and communicates at defined boundaries.
</callout>

## Subsystem Decomposition
The first architectural decision on any robot is also the most consequential: how do you split the code into pieces? Get this wrong and every other decision gets harder. Get it right and the rest mostly falls into place.
The rule professional engineers use is called the <span color="red">**`single responsibility principle`**</span>: each piece of code should have exactly one job. A <span color="red">**`subsystem`**</span> is that piece of code for a robot: a grouping of hardware and logic responsible for exactly one function, with a clear boundary around what it does and does not control.
Notice this mirrors the subsystem decomposition that mechanical engineers do when breaking down a complex machine into smaller parts. That's not a coincidence, good software architecture usually follows the mechanical boundaries of the robot, because a mechanism that moves as one physical unit is usually the thing that should be controlled by one piece of code.
<callout color="gray_bg">
	**Competition Robotics Example**
	A four-mechanism robot naturally decomposes into four subsystems:
	- **Drivetrain** converts driver joystick input into robot movement. It has no idea what "scoring" even means.
	- **Intake** runs a roller in, out, or off. It only collects or rejects a game piece, it doesn't hold one for scoring.
	- **Lift** moves a slide to a target height and reports whether it has arrived. It only controls vertical position.
	- **Outtake** opens and closes a claw to hold or release a game piece. It doesn't control its own height, it rides on the lift.
	*Lift and Outtake are separate classes even though they're physically stacked on the same mechanism, because they're controlled independently: a driver can raise the lift without opening the claw, and vice versa. Keeping them separate means a change to claw timing never touches lift code.*
</callout>

## Classes and Objects
Once you know your subsystems, you need somewhere to put each one's code. A <span color="red">**`class`**</span> is what lets you bundle a group of variables and actions together into one reusable unit, instead of leaving them scattered around your program as separate pieces you have to keep track of by hand.
Think of a class like a blueprint, or a cookie cutter. The blueprint for a house isn't a house you can live in, it's just a description of what every house built from it will have: how many rooms, where the doors go, how the plumbing connects. A class works the same way: it isn't a real, running thing, it's a description of what every object built from it will have and be able to do.
```java
class Dog {
    // fields: what every Dog remembers about itself
    name: String
    isSitting: boolean

    // constructor: builds one actual Dog from this blueprint
    Dog(dogName: String) {
        name = dogName
        isSitting = false
    }

    // methods: what every Dog can do
    bark(): void { 
	    print(name + " says woof!") 
	  }
    sit(): void { 
	    isSitting = true 
	  }
}
```
The variables that belong to a class are called its <span color="red">**`fields`**</span> (`name` and `isSitting` above), they store what one particular object remembers about itself. The methods that belong to a class are its <span color="red">**`methods`**</span> (`bark()` and `sit()` above), they're what that object can actually do. 
An <span color="red">**`object`**</span> is one real, built instance of a class, made from the blueprint: `Dog` is the blueprint, `myDog = new Dog("Rex")` builds one actual dog named Rex.  That object knows its name, `myDog.name` has the value `"Rex"`, and knows how to bark, running `myDog.bark()` will print “Rex says woof!”. 
Every class has a special method that builds a new object and sets up its starting fields is called a <span color="red">**`constructor`**</span>, it's the one method that runs automatically the moment an object is created. The constructor always shares the name of the class.  `myDog = new Dog("Rex")`  runs the Dog constructor and sets the value of the variable myDog to the new Dog object that it creates.
On a robot, each subsystem is one class, and your OpMode builds one object from it from a constructor call like `lift = new Lift(hardwareMap)`, once, near the top of your code.
Bundling a subsystem's variables and methods together like this is called <span color="red">**`encapsulation`**</span>, and it solves a real problem you'll run into the moment more than one person writes code for the same robot. Imagine the alternative: a `liftMotorPower` variable sitting in one part of your code, and a `moveLiftToHeight()` function sitting somewhere else entirely, connected only by the fact that you, personally, remember they're related. A teammate edits `moveLiftToHeight()` without realizing `liftMotorPower` also gets read somewhere else, and the lift starts behaving strangely in a way that takes an hour to track down. A `Lift` class prevents this by keeping the motor variable and the methods that touch it in one place, under one name, so nothing about the lift lives anywhere else.
Encapsulation goes one step further than just bundling things together, it also lets a class hide its own details from the rest of the program. The methods a class exposes for other code to call are its <span color="red">**`public interface`**</span>, everything else (its fields, and any private helper methods) is <span color="red">**`private implementation`**</span>: details the rest of the code doesn't need to know and shouldn't touch directly. In Java this isn't just a naming convention, `public` and `private` are real keywords you type in front of every field and method, and the compiler enforces the boundary for you: mark a field `private`, and code outside the class won't even compile if it tries to read that field directly.
This public/private boundary is what makes teamwork on the same codebase possible. As long as `Lift`'s public interface stays the same, whoever owns `Lift` can completely rewrite how it works inside (swap a simple proportional loop for a full PID controller, say) without breaking anyone else's code that calls it. Nobody else's code was ever allowed to depend on those private details in the first place.
<callout color="gray_bg">
	**Competition Robotics Example**
	```javascript
class Lift {
    // private fields: nobody outside this class touches these directly
    private slideMotor: DcMotor
    private limitSwitch: TouchSensor
    private targetHeight: int
    private state: LiftState

    // public: this is the entire contract other code can rely on
    public Lift(hw: HardwareMap) //this is the constructor
    
    public update(): void
    public setTarget(h: int): void
    public atTarget(): boolean
    public getPosition(): int

    // private method: a helper only update() calls, not part of the contract
    private computePower(error: int): double
}
	```
	`Outtake` never reads `slideMotor` or `targetHeight` directly, it only ever calls `lift.atTarget()`. That one method is the entire relationship between the two classes. Methods can be private too, not just fields: `computePower()` is an internal detail of how `update()` decides what to do, nothing outside `Lift` needs to call it directly, so marking it private means nothing outside ever will.
</callout>
<callout color="gray_bg">
	<details>
	<summary>🔵 <span color="blue">**Advanced Classes and Objects**</span></summary>
		At the basic level, knowing which methods are public and which fields are private is enough. At an advanced level, you diagram this formally with a <span color="red">**`UML class diagram`**</span>: one box per class, divided into a name, its fields, and its methods, each one marked with standard visibility notation, **+** for public, **-** for private, and each method signature written with full parameter and return types.
		<callout color="gray_bg">
			> `+ setTarget(h: int): void` reads as: a public method named setTarget, taking one integer parameter named h, returning nothing.
		</callout>
		![Example UML class diagram](media/af305df8b00de1e3.png)
		Written this precisely, a class diagram becomes a contract a teammate could implement against without ever asking you a clarifying question, exactly the same standard a subsystem requirements document holds performance requirements to.
	</details>
</callout>

## Block Diagrams
Once your subsystems exist as classes, you need a way to show how they relate to each other, and to the OpMode that runs them. A <span color="red">**`block diagram`**</span> (or component diagram) does that: one box per class, with arrows showing the relationships between them.
Three relationship types cover almost everything you'll need on a competition robot:
- <span color="red">**`composition`**</span> (drawn as a filled diamond): one object owns another, and the owned object doesn't exist independently. OpMode owns each subsystem, if the OpMode ends, the subsystems go with it.
- <span color="red">**`association`**</span> (drawn as an open arrow): one object calls methods on another, without owning it. `Outtake` calls `Lift.atTarget()`, but doesn't own the Lift.
- <span color="red">**`implements`**</span> (drawn as a dashed line with an open triangle): a class fulfills the contract defined by a shared interface (see Advanced Block Diagrams below).
Drawing this diagram before you write code answers a question that's much harder to answer by reading finished code: which subsystems actually need to know about each other, and which ones don't? If your diagram has an arrow you can't justify, that's a coupling you probably don't need.
![Example Block Diagram](media/fb41581bb0414463.png)
<callout color="gray_bg">
	<details>
	<summary>🔵 <span color="blue">**Advanced Block Diagrams: Shared Interfaces**</span></summary>
		When multiple subsystems share common behavior, instead of duplicating it in each class, define it once as an <span color="red">**`interface`**</span>: a contract listing method signatures with no implementation, that any class can promise to fulfill.
		<callout color="gray_bg">
			```javascript
interface Subsystem {
    update(): void
}
// Drivetrain, Intake, Lift, and Outtake all implement Subsystem
			```
			```javascript
// Before: OpMode calls each subsystem by name
drivetrain.update()
intake.update()
lift.update()
outtake.update()

// After: OpMode holds a list of Subsystem
for each s in subsystems:
    s.update()
// A fifth mechanism later means one new line in the list, 
// the loop itself never changes.
			```
		</callout>
		This is the same reasoning behind interface requirements in your requirements document, formalizing a boundary explicitly instead of leaving it as an informal assumption two pieces of code happen to agree on.
		In block diagram form an interface sits between the subsystems that implement an interface and the system that owns them.
		![Outtake.release() calls Lift.atTarget() first before moving the outtake servo, that boolean is the entire contract between them.](media/528df02f40311377.png)
	</details>
</callout>

## State Machines
Many subsystems and routines don't just do one thing, they move through distinct modes, and what they do next depends on which mode they're in. A lift isn't just "up" or "down," it has 3 distinct <span color="red">**`states`**</span> :
1. sitting at home
2. actively moving toward a target
3. holding at a target position against gravity, 
A `setTarget()` call means something different depending on which state the lift is currently in.
The tool for modeling this cleanly is a <span color="red">**`finite state machine`**</span> (**FSM**): a system with a fixed set of <span color="red">**`states`**</span>, where it can only be in one state at a time, and where there are explicit <span color="red">**`transitions`**</span> between them triggered by a <span color="red">**`guard condition`**</span>, the specific condition that must be true for that transition to happen.
The alternative to an explicit state machine is scattering if statements throughout your code (`isMoving`, `reachedTarget`, `wasHolding`...) and hoping their combinations never produce a state you didn't plan for. A state machine makes every valid state, and every valid path between them, something you can draw, read, and check completely before you ever run the code.
<callout color="gray_bg">
	State machines are central to FTC software design so I strongly recommend that you read the [State chapter of Game Programming Patterns](https://gameprogrammingpatterns.com/state.html) for a widely used treatment of exactly this problem, written for game and hobbyist programmers. The exact same reasoning applies to a robot's lift as to a video game character.
</callout>
<callout color="gray_bg">
	**Competition Robotics Example**
	The Lift subsystem's state machine:
	- **HOME** - motor power off
	- **MOVING** - closed-loop toward target
	- **AT_TARGET** - holds against gravity
	Transitions: 
	- **HOME** *→* **MOVING** on \[setTarget(h)\]
	- **MOVING** *→* **AT_TARGET** on \[position == target\], 
	- **AT_TARGET** *→* **MOVING** on \[setTarget(newH)\].
	*Every transition's guard condition is written in brackets. Nothing about the lift's behavior is left implicit.*
	A state machines behavior can be summarized in a state diagram.

## Main Loops
Robot code doesn't run once, top to bottom, and stop. It runs in a loop, over and over, roughly every 20 milliseconds, for the entire length of autonomous or teleop. Every subsystem's `update()` method gets called once per pass through that loop. This pattern, read input, update state, repeat, is called the <span color="red">**`main loop`**</span> (or game loop, in the game-engine world it originated from).
<callout color="gray_bg">
	See the [Game Loop chapter of Game Programming Patterns](https://gameprogrammingpatterns.com/game-loop.html) for the general version of this pattern. An FTC OpMode's `loop()` method and a video game's per-frame update are solving the exact same problem: run the same logic on a steady cycle for as long as the program is active.
</callout>
Autonomous and teleop use the same loop structure for two different jobs:
- The <span color="red">**`autonomous main loop`**</span> drives a state machine through a fixed sequence, each cycle checks whether the current step's exit condition is met, and if so, advances to the next step and issues its command once.
- The <span color="red">**`teleop main loop`**</span> continuously reads driver input and translates it into subsystem commands, every single cycle. There's no state to advance and no sequence to follow here, a driver's joystick or trigger can change from one cycle to the next, so this loop just keeps re-reading input and re-issuing commands for as long as teleop runs, whether or not anything actually changed since the last cycle.
<empty-block/>
<callout color="gray_bg">
	**Competition Robotics Example**
	Each cycle of the autonomous main loop checks the current state's exit condition. If it's met, the state advances and the next subsystem command is issued once. Drivetrain, Lift, Intake, and Outtake are only ever called with a single command per state, the state machine is what sequences them, the subsystems themselves don't know what step of autonomous they're in.
	![Example autonomous main loop](media/329a93d14614b4b8.png)
	Each cycle of the teleop main loop reads every input source it cares about, gamepad1's sticks for the drivetrain, gamepad2's triggers for intake, gamepad2's d-pad for lift, gamepad2's buttons for outtake, and turns each one into a command, all in the same pass. Unlike autonomous, there's no state being advanced here: every subsystem gets a fresh command every single cycle, whether or not the driver actually touched that control since the last one. The one exception is a guard: Outtake only honors a release if Lift reports it has reached its target, so a driver pressing the button too early does nothing until the lift catches up. That gate runs fresh, every single cycle, for the whole match.
	![Example teleop main loop](media/30b49fd64abfd8a5.png)
</callout>
<callout color="gray_bg">
	<details>
	<summary>🔵 <span color="blue">**Advanced Main Loops**</span></summary>
		At an advanced level, write the main loop as pseudocode using your real class structure, a state variable, a switch statement, and actual typed method calls, rather than boxes and arrows in a flowchart.
		<callout color="gray_bg">
			```javascript
loop():  // repeats every cycle, about 20 ms
    drivetrain.drive(gamepad1.leftStick, gamepad1.rightStick, gamepad1.turn)
    if gamepad2.rightTrigger: intake.setState(INTAKING)
    else if gamepad2.leftTrigger: intake.setState(REVERSING)
    else: intake.setState(IDLE)
    if gamepad2.aButton and lift.atTarget() and not outtake.isEmpty():
        outtake.release()
			```
		</callout>
		Notice this loop calls `intake.setState(...)`, not `intake.rollerMotor.setPower(...)`. The loop only ever talks to a subsystem through its public methods, exactly the boundary the class diagram in section 2 defined.
	</details>
</callout>

## Interfaces and Coupling
<callout color="gray_bg">
	<details>
	<summary>🔵 <span color="blue">**Advanced Interfaces and Coupling**</span></summary>
		Every relationship you draw in a block diagram is a decision about how much two subsystems depend on each other. <span color="red">**`Coupling`**</span> measures how tightly connected two pieces of code are, how much one has to know about the other's internals to work correctly. <span color="red">**`Cohesion`**</span> measures the opposite direction: how well the responsibilities *inside* one class belong together.
		High coupling is what makes a codebase fragile: change one thing, and two unrelated things break, because they were secretly relying on each other's internal details. Low cohesion is what makes a single class hard to reason about: it's doing five different jobs, so a bug report about any one of them sends you hunting through code that has nothing to do with the actual problem.
		Good architecture aims for the opposite of both: low coupling between subsystems, high cohesion within each one.
		<callout color="gray_bg">
			**Competition Robotics Example**
			The dashed line from Lift to Outtake in the block diagram is the *only* place two subsystems talk to each other directly, and it's narrow on purpose: `Outtake` asks one single boolean question, `Lift.atTarget()`. It doesn't read Lift's motor power, its target height, or its internal state, just that one method. That's loose coupling done right: a real dependency, kept as small as it can possibly be.
		</callout>
		Coupling and cohesion aren't just something you get right on day one and forget. As the season goes on and features get added, watch for warning signs that a class's cohesion is slipping: a method that's grown to five unrelated branches, two different concerns (driver input and sensor logic, say) tangled together in one `update()`, or logic duplicated in two places because nobody remembered it already existed elsewhere.
		When you spot this, propose a specific <span color="red">**`refactor`**</span>: restructuring existing code's organization without changing what it does, extracting a piece of tangled logic into its own class with its own single responsibility. Also connect your structural decisions back to their source: which requirement or KDR from Project 1 does each class, method, or guard condition actually exist to satisfy? A class diagram that can't be traced back to a real requirement is a sign you're designing the architecture you think looks impressive, not the one the robot actually needs.
	</details>
</callout>

## Putting It Together
Architecture is the set of decisions you make before you start writing code: what the pieces are, what each one owns, how they're allowed to talk to each other. Get it right, and adding a feature mid-season means writing new code in one obvious place. Get it wrong, and the same change means hunting through everything, afraid of what else it might break.
None of this replaces good code, a clean architecture with sloppy implementation still doesn't work. But architecture is what makes the implementation smooth in the first place, for you at 11pm the night before an event, and for the teammate who has to read your code after you've graduated.
