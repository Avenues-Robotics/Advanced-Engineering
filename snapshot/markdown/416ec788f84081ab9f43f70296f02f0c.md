### Overview
Nearly every mechanism on a robot has the same job: reach a target and stay there. A drivetrain stops at a position, a slide holds a height while the gripper releases, a flywheel holds a speed so every shot leaves the same way. The simplest way to program these mechanisms is open loop: run the motor at a set power for a set time and hope the result is right. That works until something changes. A battery that has dropped from 13.8 V to 12.6 V runs the motors about 9% slower, so an autonomous drive tuned to travel 150 cm in practice stops 13 cm short at competition. Added weight, worn wheels, a slightly crooked start, or a bump from another robot all have the same effect, and an open loop program has no way to notice.
**Feedback-based control** solves this problem by measuring instead of assuming. A **closed loop controller** reads a sensor, compares the measurement to the target, and adjusts its output to shrink the error, many times per second. Whatever caused the mechanism to fall short shows up in the measurement and gets corrected, even if you never predicted it. It is the same principle a thermostat, a car's cruise control, and a landing rocket booster all rely on.
In Project 5, you turn that idea into working code on your robot. You will write a reusable feedback controller class, use it to control a real mechanism from a subsystem class or an OpMode, debug it systematically, and verify on the robot that the mechanism reaches and holds its target.

### Part 2: Implement and Debug
*Goal: Build a working controller in small, verified steps, and keep a record of how you found and fixed problems.*
1. **Controller class**
	- Write your controller class in a `utility` package in TeamCode. 
	- The class should calculate the controller's output from a target and a measurement. 
	- Suggested methods include:
		- `update()`: take the current value and return a value used to power the actuator
		- `setTarget()`: set the target value for the controller
		- `atTarget()`: return whether the controller is at the target within a specified tolerance
	- Reusability: Design your controller class so it contains no hardware references. It takes a target and a measurement, returns an output, and could be used unchanged by a different mechanism or another teammate's subsystem.
		<empty-block/>
2. **Use the controller**<br>Use your controller to drive a real mechanism from a subsystem class (preferred, especially if it is your Project 4 subsystem) or directly from an OpMode.  Use telemetry to display the **target**, **measurement**, **error**, and **output** while the mechanism runs.
	<empty-block/>
	**Both the controller class and the code that uses it must:**
	- [ ] Run on a robot without errors
	- [ ] Include a Java Document Comment ([Javadoc](https://en.wikipedia.org/wiki/Javadoc#Structure_of_a_Javadoc_comment)) that describes what each class and public method does, including what each parameter means and its units.
		A class Javadoc follows this format
		```java
/**
 * Description of what the class does and what mechanism it controls.
 *
 * @author Your Name
 */
		```
		A method Javadoc follows this format
		```java
/**
 * Description of what the method does.
 *
 * @param name1 Description of parameter.
 * @param name2 Description of another parameter.
 * @return Description of return value.
 */
		```
	- [ ] Include comments that describe what each method and major section does so a reader can follow without running the code.
		<empty-block/>
3. **Commit as you go**<br>Commit each time you reach a working checkpoint, and push at the end of every session. Each commit message should say what changed and why. See <mention-page url="https://app.notion.com/p/3f6ec788f840814c880eeffd215a3bde">FTC Java 14 - Commit and Push Your Project to GitHub</mention-page> if you need a refresher.
	<empty-block/>
4. **Debugging log**<br>Document the bugs you encountered as you implemented your controller on the robot. For each one, record:
	- what you observed
	- how you reproduced it reliably
	- how you isolated the cause (telemetry, commenting out terms, setting gains to zero, etc.)
	- the cause and the fix
	- how you verified the fix actually resolved the original problem
	Your debugging log should be built from the engineering notebook entries you made during the debugging process and your commit messages. Cite or link the specific entries and commits.
	<callout icon="🐞" color="gray_bg">
		**Bug or tuning?**
		A sign error that drives the arm away from its target, an integral sum that is reset every loop, or a timer that is never reset are bugs: the code is not doing what you wrote it to do. A mechanism that overshoots because Kp is too high is a tuning issue. Your debugging log is for bugs. If you need help with gains, see <mention-page url="https://app.notion.com/p/401ec788f84081e38054deaae6f6d54c">Tuning a PIDF Controller</mention-page>.
	</callout>

### Part 3: Tune on the Robot
*Goal: Adjust your controller's gains, one change at a time, until the mechanism reaches and holds its target, and show with evidence that it works on real hardware.*
1. **Start simple**<br>Set every gain to zero except Kp. Run the mechanism between two targets and describe what you see using the vocabulary from <mention-page url="https://app.notion.com/p/3f7ec788f84081d0a468e7be52d79e62">Intro to Control Theory</mention-page>: sluggish, overshooting, oscillating, or stopping short with steady-state error.
	<empty-block/>
2. **Tune one gain at a time**<br>Follow the procedure in <mention-page url="https://app.notion.com/p/401ec788f84081e38054deaae6f6d54c">Tuning a PIDF Controller</mention-page>. Change one gain, run the mechanism again, and observe the result before changing anything else. Add the other terms (D, I, F) only when the behavior you observe calls for them.
	<empty-block/>
3. **Tuning log**<br>Record every change in your engineering notebook. For each one, record:
	- the gains you tested
	- what you observed (telemetry readings, video, or what you saw the mechanism do)
	- whether the change was an improvement, no change, or a regression
	- what you will change next, and why
	<empty-block/>
4. **Deploy and run**<br>When you are done tuning, record a short video that shows the mechanism moving to at least two different targets and holding each one, with the telemetry visible on the Driver Station or Panels graph if possible. Provide a link to your video in your submission.
	<empty-block/>
5. **Functional checklist**<br>With your final gains, state for each item below whether your controller passes, fails, or cannot be determined to pass or fail, with the evidence (telemetry readings, video, logged values) that supports your judgment.
	- [ ] The mechanism reaches the target and stops within your tolerance.
	- [ ] The mechanism holds the target without drifting away or oscillating continuously.
	- [ ] The mechanism responds correctly when the target changes.
	- [ ] Your code correctly reports when the mechanism is at its target (for example, `atTarget()`).
	- [ ] The mechanism stops safely when the OpMode is stopped.
<empty-block/>

	Your final graph should show the response you ended with and how it compares to where you started.

	<column ratio="50">
		**Proficient**
		- Classes with correctly structured fields, constructors, and methods that compile without errors and behave as intended when run.
		- Code commented to describe what each class, method, and major section does, so a reader can follow how the program works without having to run it.
		- When code doesn't work, a systematic debugging process is followed: the failure reliably reproduced, the responsible section of code isolated (for example, with telemetry/print statements or a debugger), the specific cause fixed, and the fix verified to actually resolve the original failure.

		- Code successfully deployed to the robot controller and confirmed to run as intended on the actual hardware.
	</column>
	<column ratio="50">
		**Advanced**
		In addition to Proficient…
		- Intermittent or hardware-dependent failures (something that only happens sometimes, or only on the robot and not in testing) debugged by forming a specific hypothesis about the cause and designing a test that would confirm or rule it out.
		- Branches used to develop a feature or fix without disrupting the team's working code, with changes merged back cleanly and simple conflicts resolved as they arise.
		- Code organized and named so a teammate could read and correctly modify it without a verbal explanation, with comments added where the reasoning behind a piece of code isn't self-evident from the code itself.
		- Common deployment failures recognized and prevented (code that isn't saved to the right location, a build that succeeds on a laptop but doesn't match what's on the robot, forgetting to pull a teammate's changes before running).
	</column>
