# **FTC DECODE 2025–2026**
## **Autonomous Navigation Requirements**
### **Flowdown**
This document covers the Autonomous Navigation subsystem: driving the robot and coordinating the Launcher and Intake through the autonomous period, with no driver input. These system-level shalls aren't owned by any single row of the Part 1 subsystem decomposition, since navigating the field spans all three mechanisms rather than belonging to just one.
- The robot shall score artifacts into the classifier during the autonomous period.
- The robot shall leave the starting zone during the autonomous period.
- The robot should achieve the pattern bonus during autonomous.
### **Operating Scenarios (ConOps)**
1. Close autonomous sequence
	Starting with 3 preloaded artifacts, the robot must drive to the close firing zone, tell the Launcher it's ready, confirm the shots fired, then drive to each of the three spike marks in turn, start the Intake, return to the firing zone, and fire again, all without driver input while keeping track of its own position.
2. Far autonomous sequence
	Same pattern from the far zone, with drives to the third spike mark and human player zone.
3. High-level alliance partner running in the close zone (edge case)
	With a high-level partner who clears all three spike marks and opens the gate repeatedly, drives to the secret tunnel and human player zone account for random location of artifacts leaving the gate.
4. <span color="blue">Sensor failure mid-run (failure mode)</span>
	<span color="blue">Partway through the close autonomous sequence, a wheel encoder or camera stops giving readings. The robot no longer has a trustworthy position estimate. Rather than continuing to drive toward a target it can't actually confirm, the software recognizes the failure and shuts the robot down safely where it is.</span>
### **Functional requirements**
1. The navigation software shall keep track of the robot's position and which way it's facing throughout the autonomous period.<br><span color="blue">Rationale: every other functional requirement depends on knowing where the robot is. Without this, the robot can't aim, can't tell whether it has arrived, and can't tell whether it's driving toward or away from its target.</span>
2. The navigation software shall drive the robot from its current position to each target location (firing zone, spike mark, human player zone) during the autonomous period.<br><span color="blue">Rationale: derived directly from the system-level requirement to score during autonomous. The robot can't fire on or collect from a location it never reaches.</span>
3. The navigation software shall tell the Launcher it's safe to fire only after confirming the robot has reached the firing zone.<br><span color="blue">Rationale: prevents a wasted or inaccurate shot fired from the wrong position, which costs both the artifact and the time spent traveling there.</span>
4. The navigation software shall drive the robot out of the starting zone within the first 1 seconds of the autonomous period.<br><span color="blue">Rationale: directly satisfies the system-level requirement to leave the starting zone, which scores points on its own regardless of shooting accuracy. The earlier the robot leaves, the more of the autonomous period is left for scoring actions.</span>
### **Performance requirements**
**Shall Requirements**
1. Position accuracy: The robot's position estimate <span underline="true">shall</span> be accurate to within 2 cm, and its heading to within 2 degrees, under normal conditions.
	<span color="blue">Rationale: ties directly to the firing-position accuracy requirement and to reaching spike marks without colliding with field walls or other robots. If the estimate drifts beyond a few centimeters the robot can miss the firing zone or clip an obstacle.</span>
	<span color="blue">MOP: Run the robot through the full close-zone route 5 times, checking the estimated position against a fixed tape line at each waypoint. Pass = estimate within tolerance at every waypoint in at least 4 of 5 runs.</span>
	<span color="blue">TPM: Track measured position error at each waypoint across build iterations. Predicted value at project start: 5 cm using wheel encoders alone, improving as additional sensors are added.</span>
2. Path completion time: The software <span underline="true">shall</span> finish the close-zone, three-spike-mark route with enough time left in the 30-second autonomous period to attempt at least 3 shooting sequences.
	<span color="blue">Rationale: derived from the 30-second autonomous period and the goal of attempting at least 3 firing sequences. A route that takes too long leaves points on the table no matter how accurate the aim is.</span>
	<span color="blue">MOP: Time 5 full autonomous runs from the start signal, recording how many firing sequences were completed. Pass = at least 3 sequences completed in 5 of 5 runs.</span>
	<span color="blue">TPM: Track sequences completed per run across iterations. Predicted value at project start: 2 sequences.</span>
3. Loop speed: The navigation software <span underline="true">shall</span> check its position and update its driving decisions at least every 20 milliseconds.
	<span color="blue">Rationale: a robot that checks its position too infrequently reacts late to a wall, another robot, or drift, so the loop has to run fast enough that little changes between checks.</span>
	<span color="blue">MOP: Log loop execution time in code across a full match-length run and confirm it stays at or under 20 ms. Pass = 100% of loops at or under 20 ms.</span>
	<span color="blue">TPM: Track average and worst-case loop time as more sensors and logic are added. Predicted value at project start: 15 ms.</span>
4. Firing-position accuracy: The robot <span underline="true">shall</span> be within 5 cm of the intended firing spot before telling the Launcher to fire.
	<span color="blue">Rationale: matches the positional margin the Launcher's own aim can tolerate. This value should be confirmed with the Launcher subsystem owner rather than assumed.</span>
	<span color="blue">MOP: Measure the robot's actual stopped position against the intended firing spot over 10 approaches. Pass = within tolerance in 9 of 10 approaches.</span>
	<span color="blue">TPM: Track measured position error at each iteration. Predicted value at project start: 8 cm.</span>
5. Stuck detection: The software <span underline="true">shall</span> notice within 300 ms if the robot has stopped making progress toward where it's trying to go.
	<span color="blue">Rationale: a robot that keeps pushing into a wall or another robot without noticing wastes the rest of autonomous doing nothing productive. Catching this quickly is what makes any recovery action possible at all.</span>
	<span color="blue">MOP: Deliberately block the robot's path in testing and time how long the software takes to recognize no progress is being made. Pass = detected within 300 ms in 5 of 5 induced trials.</span>
	<span color="blue">TPM: Track measured detection time across iterations. Predicted value at project start: 300 ms.</span>
### **Interface requirements**
1. The navigation software <span underline="true">shall</span> tell the Launcher subsystem "ready to fire" only once the robot's position meets the firing-position accuracy requirement above, not just after a fixed amount of driving time. *(Confirmed with Launcher subsystem owner.)*
	<span color="blue">Rationale: without this gate, the software could tell the Launcher to fire based on a guess or elapsed time instead of a confirmed position, defeating the purpose of tracking position at all.</span>
2. The navigation software <span underline="true">shall</span> drive the robot using the same motor commands used during teleop, so the same tested driving code is reused instead of a separate autonomous-only version.
	<span color="blue">Rationale: reusing the teleop drive code means autonomous inherits behavior that's already been exercised by the driver in practice, instead of running brand-new, unverified code for the first time in a match.</span>
3. The navigation software <span underline="true">shall</span> read its position sensors (wheel encoders and/or a camera) as often as they update, and if a sensor stops giving new readings, the software shall notice and ensure safe shutdown of the robot to avoid entering the opposing alliance's side.
	<span color="blue">Rationale: this is the software's defined response to the Sensor dropout handling Key Driving Requirement below. Without a defined shutdown behavior, this failure mode has no defined outcome and the robot's behavior becomes unpredictable.</span>
4. The navigation software <span underline="true">shall</span> start the Intake subsystem's collection sequence once it confirms the robot has arrived at a spike mark, not just after a fixed amount of driving time. *(Confirmed with Intake subsystem owner.)*
	<span color="blue">Rationale: gating on position confirmation, not elapsed time, keeps the Intake from starting early at the wrong spot or late after the robot has already moved on.</span>
### **Should requirements**
1. The navigation software <span underline="true">should</span> complete the pattern-bonus artifact arrangement during autonomous when there's time for it, without risking the higher-value classifier scoring cycles.
	<span color="blue">Rationale: the pattern bonus is worth fewer points than the classifier scoring cycles, so it's explicitly optional. Chasing it should never come at the expense of the higher-value action.</span>
	<span color="blue">MOP: Run 5 full autonomous sequences and check whether the pattern-bonus arrangement was completed without adding time to the classifier-scoring cycles. Pass = bonus completed with no added time in at least 3 of 5 runs.</span>
	<span color="blue">TPM: Track how many runs achieve the bonus without a time penalty across iterations. Predicted value at project start: 0 of 5, not yet attempted.</span>
2. The navigation software <span underline="true">should</span> record where the software thought the robot was versus where it actually ended up at the end of autonomous, to help tune paths between events.
	<span color="blue">Rationale: without a record of predicted versus actual position, tuning the path between competition events relies on guesswork instead of evidence.</span>
	<span color="blue">MOP: Confirm a log or printed report exists after each autonomous run showing predicted vs. measured end position. Pass = log present and correct after 5 of 5 runs.</span>
	<span color="blue">TPM: Track average end-of-run position error shown in the log across iterations. Predicted value at project start: 10 cm.</span>
### **Key Driving Requirements**
1. Position accuracy
	Hardest to verify early. Small position errors add up over many waypoints across a full autonomous run, so a robot that looks accurate on the first waypoint in testing can still drift off by the last one.
2. Sensor dropout handling
	High risk for major penalties. If the software doesn't catch a wheel encoder or camera losing its signal immediately, a robot that no longer knows where it is can drive into the opposing alliance's side instead of shutting down safely.
