Before writing a single line of code, good engineers decide how the software will be organized: what classes exist, what each one is responsible for, and how they communicate. An architecture sketched out in advance, rather than discovered by accident while coding, is what lets a software team work on the same system without constantly stepping on each other's code.
The[ System Architecture Reading](/p/3e5ec788f84081649622dde7cda294aa?pvs=25) is your primary resource for learning how software engineers think about system architecture and the various diagrams they use to communicate the structure of a software system.  
You should also review the two exemplars at the end of the assignment description.

**Required sections:**
1. **Robot Overview**
	A short paragraph describing the robot's mechanisms and what autonomous and teleop are each trying to accomplish. Orient a reader who has never seen the robot.
2. **Subsystem Breakdown**
	For each subsystem, state what it is responsible for, what mechanical hardware it wraps, and what it explicitly does not do. One subsystem should not know about or control another subsystem's job.  You can break this down in paragraph or table form.
	<callout icon="2️⃣" color="gray_bg">
		**For SCS2 (advanced option for SCS1)**
		Replace this section with a formal class diagram using standard UML notation: each subsystem's fields, constructor, and method names (with parameter and return types), and public/private visibility.
	</callout>
3. **System Block Diagram**
	A block diagram showing every subsystem and the relationships between them: which ones coordinate, share information, or depend on another subsystem's state.
	<callout icon="2️⃣" color="gray_bg">
		**For SCS2**
		Use standard relationship notation (a dashed arrow with an open triangle for *implements*, a filled diamond for *owns*, an open arrow for *calls*). Where multiple subsystems share common behavior, show it as a shared *interface* and explain why that reduces duplicated code.
	</callout>
4. **State Diagram(s)**
	Think about how you would use a **state machine** for at least one subsystem (intake, shooter, etc.) or op mode (auto or teleop).  Create a box and arrow diagram of the states and the conditions that move between them.
	<callout icon="2️⃣" color="gray_bg">
		**For SCS2**
		Name the entry action for each state (what actually happens on arrival) and write guard conditions in bracket notation, e.g. \[rightTrigger\], rather than as plain phrases.
	</callout>
5. **Autonomous Main Loop**
	Create a box and arrow diagram of the robot's autonomous main loop: what gets checked or called each cycle, and in what order.
	<callout icon="2️⃣" color="gray_bg">
		**For SCS2**
		Write this as pseudocode against your real class structure from section 2 (a state variable, a switch statement, actual method calls) instead of labeled diagram boxes.
	</callout>
6. **Teleop Main Loop**
	Same as above, for the tele-operated period: what each driver's input maps to, and what gets checked or called each cycle.
	<callout icon="2️⃣" color="gray_bg">
		**For SCS2**
		Also written as pseudocode against your real class structure.
	</callout>
7. **Design Rationale**
	Explain why the architecture is organized the way it's diagrammed. Connect each subsystem's responsibility to a specific mechanism or function in the mechanical design.
	<callout icon="2️⃣" color="gray_bg">
		**For SCS2, replace this section with Traceability to Requirements**
		A table connecting specific structural decisions (a class, a method, a guard condition) back to specific requirements or KDRs from Project 1, the same way a CAD design gets verified against requirements.
	</callout>

## Rubric
### Software Architecture
<columns>
	<column ratio="50">
		**Proficient**
		- The software subsystems the robot needs identified from its mechanical design, with each one's responsibility stated and matched to the mechanical decomposition.
		- A block or component diagram of the relationships between subsystems, showing which subsystems need to coordinate or share information.
		- For any subsystem or autonomous routine with distinct modes, a diagram of the states and the conditions that move between them.
		- A diagram of the robot's autonomous and tele-operated main loops, showing what gets checked or called each cycle and in what order.
		- An explanation of why the architecture is organized the way it's diagrammed, connecting each subsystem's responsibility to a specific mechanism or function in the mechanical design.
	</column>
	<column ratio="50">
		**Advanced**
		In addition to Proficient…
		- The whole-robot functional architecture translated into a class structure, with each subsystem's fields, constructor, and methods defined, and pseudocode written for the autonomous and tele-operated main loops that calls the real methods defined in that structure.
		- Each class's public interface distinguished from its internal implementation.
		- Each subsystem's or routine's state model represented as an explicit state data structure (ex. enum) inside the class.
		- When a mechanism or requirement changes mid-season, a decision on whether the change belongs in a new class or an existing one, justified by responsibility rather than convenience.
		- An explanation of each class's structure defending the data structures chosen and boundary between public and internal data and methods.
	</column>
</columns>
### Technical Writing
<columns>
	<column ratio="50">
		**Proficient**
		- Written explanations that connect a design decision, test result, or prediction to the underlying engineering reasoning, requirement, or physics, using accurate technical vocabulary.
		- A clear, specific claim about whether a design meets a requirement, supported by evidence such as test data, CAD verification, or calculations.
		- Evidence that is relevant and sufficient to support the claim, including quantitative evidence (measurements, calculations, statistics) where available.
		- Because technical writing is a developing skill, proficient work successfully communicates the claim and evidence, but may contain minor errors in organization, clarity, or vocabulary use.
	</column>
	<column ratio="50">
		**Advanced**
		- Explanations and arguments that are logically coherent, using clear, quantitative reasoning to connect evidence to the claim rather than asserting a conclusion.
		- Quantitative reasoning used to reflect on the strength of the claim, including its limitations, sources of uncertainty, or where more evidence would be needed.
		- Writing that is concise and efficient, communicating complex engineering ideas at a level of depth and technicality appropriate to the intended audience (a teammate, a judge, a general reader).
		- Clear multi-paragraph structure that separates distinct ideas, design intent, evidence, and conclusion, rather than blending them together.
	</column>
</columns>
